<verified_facts>
These were verified against the worker source AND empirically against the live images
during planning. Treat as ground truth — they shape the implementation:

1. The worker captures ONLY top-level files in `/workspace` as artifacts
   (ReadArtifacts, internal/runner/docker.go:669-723). Subdir files are ignored, and
   there is NO size filter — blank/zero-byte files ARE captured. PNGs MUST be written to
   `/workspace/*.png` directly, and devices MUST open LAZILY so a no-plot run emits nothing.
2. cwd of user code is `/workspace`; runtime UID is 65534, rootfs is read-only,
   `--network=none`. All installs happen at BUILD time. Both new aux files
   (sitecustomize.py, Rprofile.site) must be world-readable so UID 65534 reads them.
3. There is NO per-job env injection (no Env field on manifest/JobSpec). Everything must
   be baked via Dockerfile ENV or placed in an auto-loaded location.

VERIFIED DURING PLANNING (do not re-litigate — implement as stated):

A. R STARTUP PATH — the current Dockerfile writes `/etc/R/Rsite.profile`, which is DEAD
   CODE. R never sources a file by that name. On r-base:4.4.2: R_HOME=/usr/lib/R;
   `/usr/lib/R/etc/Rprofile.site` is a SYMLINK to `/etc/R/Rprofile.site`. The ONLY
   auto-sourced site profile is `Rprofile.site`. => COPY our profile to
   `/etc/R/Rprofile.site`. The old Rsite.profile RUN block must be REMOVED (its flush
   callback never actually ran). Our new profile carries the flush callback forward, so
   streaming behavior is preserved, not lost.

B. R LAZY DEVICE — the `setHook("plot.new", ...)` form is BROKEN: opening a device inside
   the plot.new hook resets device state and the subsequent plot.xy fails with
   "plot.new has not been called yet". The CORRECT hook is
   `setHook("before.plot.new", fn, action="replace")` — it fires BEFORE plot.new on the
   (fresh) device. Empirically: 2 plots => exactly 2 PNGs; 0 plots => 0 PNGs; error after
   1 plot => the finalizer flushes that 1 PNG. Use `before.plot.new`.

C. PYTHON FIGURE CAPTURE — a naive atexit saver registered from sitecustomize sees
   `get_fignums() == []` because matplotlib registers `atexit.register(Gcf.destroy_all)`
   when `_pylab_helpers` imports, and since sitecustomize runs first, our handler runs
   LAST (LIFO) — after destroy_all wiped everything. The WORKING fix (verified to produce
   2 PNGs): wrap `builtins.__import__`; on the first `matplotlib*` import, UNREGISTER
   `Gcf.destroy_all` and register OUR saver that saves all figures THEN calls
   `Gcf.destroy_all`. Exact contract is in Task 1.

D. PYTHON PINS — all resolve as manylinux wheels against numpy 2.2.6 / matplotlib 3.10.3
   / pandas 2.2.3 with NO conflicts (verified build): scipy==1.15.3, statsmodels==0.14.4,
   scikit-learn==1.6.1, seaborn==0.13.2, cvxopt==1.3.2, swiglpk==5.0.12, PICOS==2.6.0.
   `swiglpk` BUNDLES GLPK — NO apt libglpk package is needed; PICOS solves with
   `solver='glpk'` out of the box. So the Python image needs ZERO new apt deps. (If any
   pin ever fails to resolve, network IS available during `docker build` — loosen that one
   pin to the nearest compatible release.)

E. PYTHON MPLCONFIGDIR — UID 65534's home is `/nonexistent`; matplotlib prints a noisy
   "mkdir failed for /nonexistent/.config/matplotlib" warning and falls back to a temp dir.
   Bake `ENV MPLCONFIGDIR=/tmp/mplconfig` to silence it. (At runtime the rootfs is
   read-only but `/tmp` is a writable tmpfs in the sandbox; matplotlib only needs a
   writable cache dir, and degrades gracefully if absent.)

F. MEASURED (probe build): final Python image ~697MB, heavy-stack import ~1.3s. These are
   reference numbers; Task 3 reports the actual built-image numbers.
</verified_facts>
