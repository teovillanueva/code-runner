<objective>
Stand up the local dev stack and prove the whole interactive slice end-to-end. docker compose brings
up api + worker (with the host docker socket mounted, no DinD) + redis + soketi + a stub upstream app.
The stub plays the role of the user's backend: it calls the API to execute an interactive Python
program, subscribes to the soketi channel, signals start, sends stdin, prints the streamed output,
and awaits the terminal result. A documented script runs the full punta-a-punta flow and asserts it.

Purpose: DEV-01 (compose stack), DEV-02 (stub drives interactive execute), DEV-03 (documented script
walks the E2E). This is the phase's UI-hint deliverable: the first time `/execute → subscribe → /start
→ stdin → streamed output → result` works against the real stack.

Output: docker-compose.yml, per-app Dockerfiles, apps/stub, scripts/e2e.sh, README quickstart section,
and Makefile/`.env.example` wiring.

This plan is NOT autonomous: it contains a blocking human-verify checkpoint because the streamed
interactive demo is timing/soketi-dependent and benefits from a human confirming the live behavior.
</objective>

 1. POST {API}/v1/execute with Bearer EXECUTOR_API_TOKEN and an interactive python program whose
    main.py does e.g. `name = input("name? "); print(f"hello {name}")` → capture {jobId, channel}.
 2. Connect pusher-js to the soketi host with the app key (cluster/host config for self-hosted soketi),
    subscribe to channel (private-run-<jobId>). For private channels soketi calls an auth endpoint —

 4. After subscription is confirmed, POST /v1/jobs/:id/start (this is the handshake — start AFTER subscribe).
 5. On seeing the prompt, POST /v1/jobs/:id/stdin {chunk:"World\n"}; optionally /stdin/close.
 6. Resolve/exit 0 when the result event arrives with exitCode 0; exit non-zero on timeout.
Make the program parameters (host/port/token) come from env so compose and scripts can drive it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stub → API | the stub is the trusted upstream app; it authenticates with EXECUTOR_API_TOKEN |
| host socket → worker | the worker container mounts the host docker socket (root-equivalent) — it is a trusted component; the socket is NEVER mounted into a sandbox |
| soketi → client | output-only; the stub never sends trusted input via soketi |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-14 | Elevation of Privilege | docker socket mount | mitigate | Socket mounted ONLY into the worker (trusted), never into a sandbox; sandboxes are --network=none with no socket bind (Phase 2 + PITFALLS §4) |
| T-03-15 | Information Disclosure | soketi secret in compose | mitigate | Secret supplied via env to soketi + worker only; never written to Redis; no endpoint returns it (CFG-02) |
| T-03-SC | Tampering | npm install pusher-js (stub) + docker images redis/soketi | mitigate | pusher-js is the official Pusher client; redis:7 and soketi 1.x are pinned official images; versions pinned in compose/package.json |
| T-03-16 | Spoofing | stub → API auth | mitigate | Stub sends Bearer EXECUTOR_API_TOKEN; the API's constant-time middleware (Plan 04) gates it |
</threat_model>
